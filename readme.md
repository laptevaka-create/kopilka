# Копилка

### Учёт личных финансов

**Копилка — настольное приложение для ведения личного бюджета: доходы и расходы по категориям, месячные лимиты, отчёты, CSV-обмен и регулярные платежи.**

> Электронная таблица отвечает на вопрос «сколько потратила в мае?».
> Копилка отвечает на вопрос **«сколько ещё можно тратить до конца месяца?»**

Курсовой проект по дисциплине «Разработка программных модулей».
C# + WPF + MVVM + SQLite, работа полностью локальная.

Документы проекта:

| Файл | Что в нём |
| --- | --- |
| `readme.md` | **Источник истины**: концепция, объём MVP, схема БД, порядок работ, демо-сценарий, сборка |
| `docs/tz.md` | Техническое задание (ГОСТ 19.201), сдаётся отдельно |
| `docs/specs/data-model.md` | Спецификация модели данных: таблицы, нормализация, справочники |

## Проблема

Типичный учёт личных финансов без приложения:

```text
зарплата          120 000 ₽
аренда            −35 000 ₽
продукты          −18 000, −12 400, −9 800 ₽   (несколько заходов)
подписки          −2 500 ₽                     (и ещё три по мелочи)
«куда делись деньги» — в конце месяца
```

Учёт в голове не работает: суммы забываются, мелкие повторяющиеся траты
невидимы, а бюджет узнаёт о превышении постфактум. Электронная таблица
решает половину задачи: фиксирует факты, но не отвечает на вопрос
«сколько доступно в день, чтобы уложиться в лимит».

Копилка закрывает связку: **факт → категория → лимит → статус → решение**.

---

## Решение

```text
Транзакция → Категория → Бюджет месяца → Статус («в норме / внимание / превышен»)
          → Отчёт по категориям → CSV импорт/экспорт
          → Регулярные платежи → автоначисления по расписанию
```

Пять базовых сущностей:

- **Счёт** — «Наличные», «Карта» или собственный; где лежат деньги;
- **Категория** — «доход» или «расход», имя; категория расхода может иметь лимит;
- **Транзакция** — счёт, категория, сумма, дата, комментарий. Одна строка журнала;
- **Бюджет** — лимит на категорию в конкретном месяце;
- **Регулярный платёж** — шаблон: категория, сумма, день месяца.

Поверх них — детерминированные движки расчёта (статусы бюджетов,
генерация регулярных начислений, валидация CSV, сальдо): чистые функции
без обращений к базе и интерфейсу, каждая ветка покрыта юнит-тестами.

## Принципы

Зафиксированы и не обсуждаются в рамках MVP:

1. **Обычный пользователь.** Без админских прав, без служб, без автозапуска.
2. **Локально.** Данные в `%LOCALAPPDATA%\Kopilka`. Сетевых вызовов нет вообще:
   ни телеметрии, ни облака, ни обновлений из интернета.
3. **Одна валюта.** Всё в рублях. Мультивалютность — вне MVP.
4. **Копейки — целым числом.** Все суммы хранятся в копейках (`long`).
   Ошибок плавающей точки при суммировании нет по построению; в рубли
   сумма переводится только на выводе.
5. **SQLite без EF.** `Microsoft.Data.Sqlite`, SQL-запросы пишутся напрямую.
   Схема версионируется через `PRAGMA user_version`, миграции —
   SQL-файлы, встроенные в сборку.
6. **MVVM свой.** `ViewModelBase` и `RelayCommand` написаны в проекте
   (~30 строк + ICommand), без сторонних MVVM-библиотек. Модели
   представления не знают про View и тестируются юнит-тестами без UI.
7. **UI тонкий, на русском.** WPF — только оболочка. Бизнес-логики
   в окнах нет. Английские имена — только в коде.
8. **Честная деградация.** Битый CSV, занятая база, отсутствующий каталог —
   понятное сообщение и продолжение работы, а не падение.
9. **Проверяемость.** Каждый шаг заканчивается сборкой без ошибок
   и предупреждений (`TreatWarningsAsErrors`), зелёными тестами,
   коммитом и записью в дневник.

Стек MVP:

```text
Windows + .NET 10 (net10.0-windows) + WPF + MVVM + SQLite (Microsoft.Data.Sqlite)
```

Сторонние пакеты исчерпываются списком: `Microsoft.Data.Sqlite`,
`Microsoft.Extensions.DependencyInjection`, `Microsoft.Extensions.Logging`;
в тестах — `xunit`. Прочих зависимостей нет и не планируется.

## Чего Копилка не делает

Граница проекта. Отвечает на вопрос «а почему нет…» до того, как он задан.

```text
НЕ ходит в сеть: ни синхронизации, ни облака, ни телеметрии
НЕ поддерживает мультивалютность и курсы обмена
НЕ рассчитывает налоги и кредиты
НЕ ведёт нескольких пользователей и не запрашивает пароль на вход
НЕ строит прогнозы и советы: только факты и статусы
НЕ работает в фоне: нет процессов, кроме запущенного приложения
```

Данные принадлежат пользователю: одна папка в `%LOCALAPPDATA%`,
полное удаление — одна кнопка в настройках (шаг 7).

## Архитектура

Два проекта. Разделение — не косметика: один csproj делает правило
«Core не знает про UI» проверяемым ограничением, а не комментарием.

> Структура создана на шаге 0: `src/Kopilka.Core` (`net10.0`),
> `src/Kopilka.App` (`net10.0-windows`, на выходе `Kopilka.exe`),
> `tests/Kopilka.Core.Tests` (xunit). Решение — классический `Kopilka.sln`
> (не `.slnx`, чтобы открывался любым Visual Studio и любым SDK).

```text
Kopilka.sln
│
├── src/Kopilka.Core      (net10.0 — переносимое ядро, без WPF и WinAPI)
│   ├── Time            IClock, SystemClock
│   │                   (функция времени за интерфейсом — движки
│   │                   тестируются на фиксированных датах)
│   ├── Storage         AppPaths: %LOCALAPPDATA%\Kopilka, kopilka.db,
│   │                   kopilka.demo.db
│   ├── Domain          Account, Category, Transaction, Budget,
│   │                   RecurringPayment, Setting          (шаг 1)
│   ├── Engines         BudgetEngine, RecurringEngine, CsvValidator,
│   │                   BalanceEngine                       (шаги 4–6)
│   └── Data            SqliteRepository, миграции через
│                       PRAGMA user_version                (шаг 1)
│
├── src/Kopilka.App       (net10.0-windows — WPF, оболочка и композиция)
│   ├── App.xaml.cs     DI-контейнер: регистрация сервисов Core,
│   │                   выбор обычного или демо-режима (--demo)
│   └── Presentation    MainWindow, ViewModelBase, RelayCommand,
│                       модели представления                 (шаг 2+)
│
└── tests/Kopilka.Core.Tests  (net10.0, xunit; включая архитектурный тест,
                               что Core не ссылается на Windows-стеки)
```

### Направление зависимостей

Стрелка «A → B» означает «A зависит от B».

```text
        ┌──────────────┐
        │ Presentation │   WPF — только оболочка
        └──────┬───────┘
               ▼
        ┌──────────────┐
        │     Core     │   домен, движки, доступ к данным
        └──────────────┘
```

App зависит от Core, Core не зависит ни от кого: ни от WPF, ни от
Windows-стеков. Отсюда проверяемый тезис: **ядро переносимо, оболочка
заменяема** — логика тестируется без UI, а при желании WPF меняется
на любую другую оболочку без правки Core.

## MVP Scope

### Must

**Справочники**

- счета: «Наличные», «Карта» предустановлены, свои можно добавить;
- категории: имя, тип «доход/расход», признак лимита;
- удаление используемых счёта/категории запрещено, с сообщением причины.

**Журнал транзакций**

- добавление, редактирование, удаление через диалог;
- список за месяц: дата, счёт, категория, комментарий, сумма;
- итоги: доходы, расходы, сальдо; пересчёт сразу после изменения;
- фильтр по категории и произвольному периоду.

**Бюджеты**

- лимит на категорию расхода в месяце;
- статусы «в норме / внимание (≥ 80 %) / превышен»;
- «доступно в день»: остаток на оставшиеся дни месяца.

**Отчёты и CSV**

- отчёт месяца по категориям: суммы и доли;
- экспорт месяца в CSV (`;`, UTF-8);
- импорт CSV с построчной валидацией и отчётом «импортировано X,
  пропущено Y» с причинами по каждой пропущенной строке.

**Регулярные платежи**

- шаблоны: категория, сумма, день месяца, активность;
- автоначисления при запуске и открытии месяца, без дублей;
- 31-е число в коротком месяце → начисление в последний день месяца.

**Прочее**

- настройки: счёт по умолчанию, параметры «ключ—значение»;
- полное удаление данных: база стирается и пересоздаётся пустой;
- демо-режим `Kopilka.exe --demo`: отдельная база с реалистичным месяцем.

### Non-goals (после MVP)

- мультивалютность, курсы, конвертация;
- облако, синхронизация, мобильные клиенты;
- OCR чеков, импорт банковских выписок;
- графики и аналитика сложнее отчёта месяца;
- пароль, шифрование базы, несколько пользователей.

Цель семестра — не «финансовый комбайн», а:

> **Доказать связку «факт → категория → лимит → статус» end-to-end
> на одном реальном сценарии месяца.**

## Схема БД

SQLite, файл `%LOCALAPPDATA%\Kopilka\kopilka.db`. Миграции — SQL-скрипты
вручную через `PRAGMA user_version`, без EF. Даты хранятся строками ISO
(`YYYY-MM-DD`) — читается глазами, сортируется как текст, не зависит
от формата календарных типов.

```sql
-- V001 — начальная схема

-- Справочник счетов: «Наличные», «Карта», пользовательские
CREATE TABLE accounts (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL UNIQUE,
    sort_order  INTEGER NOT NULL DEFAULT 0,
    is_default  INTEGER NOT NULL DEFAULT 0
);

-- Справочник категорий. kind: income | expense.
-- has_limit — по категории расхода задаётся месячный бюджет.
CREATE TABLE categories (
    id          INTEGER PRIMARY KEY,
    name        TEXT NOT NULL,
    kind        TEXT NOT NULL CHECK (kind IN ('income', 'expense')),
    has_limit   INTEGER NOT NULL DEFAULT 0 CHECK (has_limit IN (0, 1)),
    sort_order  INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX ix_categories_name_kind ON categories (kind, name);

-- Транзакции. Сумма всегда положительная в копейках:
-- направление задаётся типом категории, а не знаком числа.
CREATE TABLE transactions (
    id              INTEGER PRIMARY KEY,
    account_id      INTEGER NOT NULL REFERENCES accounts (id),
    category_id     INTEGER NOT NULL REFERENCES categories (id),
    amount_kopecks  INTEGER NOT NULL CHECK (amount_kopecks > 0),
    date            TEXT NOT NULL,        -- 'YYYY-MM-DD'
    comment         TEXT
);
CREATE INDEX ix_transactions_date          ON transactions (date);
CREATE INDEX ix_transactions_category_date ON transactions (category_id, date);
CREATE INDEX ix_transactions_account_date  ON transactions (account_id, date);

-- Месячные бюджеты: одна строка на (категория, месяц)
CREATE TABLE budgets (
    id              INTEGER PRIMARY KEY,
    category_id     INTEGER NOT NULL REFERENCES categories (id),
    month           TEXT NOT NULL,        -- 'YYYY-MM'
    limit_kopecks   INTEGER NOT NULL CHECK (limit_kopecks > 0),
    UNIQUE (category_id, month)
);

-- Шаблоны регулярных платежей
CREATE TABLE recurring (
    id              INTEGER PRIMARY KEY,
    category_id     INTEGER NOT NULL REFERENCES categories (id),
    account_id      INTEGER NOT NULL REFERENCES accounts (id),
    amount_kopecks  INTEGER NOT NULL CHECK (amount_kopecks > 0),
    day_of_month    INTEGER NOT NULL CHECK (day_of_month BETWEEN 1 AND 31),
    comment         TEXT,
    is_active       INTEGER NOT NULL DEFAULT 1 CHECK (is_active IN (0, 1)),
    last_applied    TEXT                  -- 'YYYY-MM-DD', защита от дублей
);
CREATE INDEX ix_recurring_active ON recurring (is_active);

-- Настройки вида ключ—значение
CREATE TABLE settings (
    key     TEXT PRIMARY KEY,
    value   TEXT NOT NULL
);
```

Как это используется:

- журнал месяца — `SELECT … FROM transactions WHERE date BETWEEN ? AND ? ORDER BY date, id`;
- итоги — `SUM(amount_kopecks)` в соединении с категориями, разделение
  по `kind` на доходы и расходы;
- панель бюджетов — бюджеты месяца + суммы транзакций по тем же категориям;
- регулярные начисления — шаблоны + `last_applied` (прошлые начисления
  не повторяются);
- настройки — счёт по умолчанию и прочие ключи.

Нормализация: сумма повторяется только в `transactions`; имя категории
и счёта — только в справочниках; транзакция ссылается на справочники
по идентификаторам. Деноминации и переименования категорий касаются
справочников, а не истории.

## Детерминированные движки

Вся логика расчётов — чистые функции: входы → выход, без базы и без UI.
Каждая ветка решения покрыта юнит-тестами на фиксированных входных данных.

### BudgetEngine

Вход: `лимит, потрачено, текущий день, дней в месяце`. Выход: статус
и «доступно в день».

```text
status:
  "в норме"     потрачено <  80% лимита
  "внимание"    80% лимита ≤ потрачено < лимит
  "превышен"    потрачено ≥ лимит

available_per_day (для «в норме» и «внимание»):
  (лимит − потрачено) / (дней в месяце − текущий день + 1)
```

Границы (порог 80 % включительно, «доступно в день» считает текущий
день оставшимся) покрыты тестами явно.

### RecurringEngine

Вход: `шаблон (день месяца), диапазон дат`. Выход: список дат начислений.

```text
дата начисления в месяце = min(day_of_month, дней в месяце)
31-е в 30-дневном месяце   → 30-е
31-е в феврале             → 28-е или 29-е (високосность учитывается)
```

### CsvValidator

Вход: строки CSV. Выход: валидные транзакции + список ошибок
с номерами строк и причинами (битая дата, неположительная сумма,
неизвестная категория, неверное число колонок). Ничего не бросает
исключений наружу: результат импорта всегда отчёт
«импортировано X, пропущено Y».

### BalanceEngine

Вход: транзакции периода. Выход: сумма доходов, сумма расходов, сальдо,
сальдо по счёту. Целые копейки: суммирование без округлений.

Полные нормативные спецификации — [`docs/specs/finance-rules.md`](docs/specs/finance-rules.md)
(создаётся на шаге 4 вместе с первым движком).

## Порядок доведения до MVP

Вертикальный срез: сначала журнал и факты, затем контроль и автоматика.
CSV и регулярные платежи — в конце: они опираются на уже работающий
журнал и категории.

| # | Шаг | Критерий готовности |
| --- | --- | --- |
| 0 | **Каркас.** Два проекта, DI, `IClock`, `AppPaths`, пустое окно | Core собирается без `-windows`; сборка 0/0 |
| 1 | **Домен + SQLite.** Модели, миграции `PRAGMA user_version`, репозиторий | БД создаётся первым запуском; тесты репозитория зелёные |
| 2 | **MVVM + журнал.** `ViewModelBase`, `RelayCommand`, окно месяца, диалог добавления | Добавление видно в списке без перезапуска |
| 3 | **Категории + фильтры.** Управление категориями, фильтр по категории/периоду, редактирование | Фильтр работает, итоги пересчитываются |
| 4 | **Бюджеты.** `BudgetEngine`, панель статусов | Все ветки статуса покрыты тестами |
| 5 | **Отчёт + CSV.** Отчёт месяца, экспорт, импорт с валидацией | Импорт битого файла не роняет приложение, даёт отчёт по строкам |
| 6 | **Регулярные платежи.** `RecurringEngine`, автоначисления | Начисления детерминированы, границы покрыты тестами |
| 7 | **Настройки + удаление.** Окно настроек, полное удаление данных | Удаление стирает БД и пересоздаёт пустую |
| 8 | **Демо.** `--demo`: отдельная база с реалистичным месяцем | Демо работает на чистой машине без ручной настройки |
| 9 | **Финал.** Полировка, README, отчёт, шпаргалка защиты | Полный прогон на чистой папке |

## Демо-сценарий (защита)

```text
1.  Запустить Kopilka.exe --demo на учебном ПК (обычный пользователь)
2.  Открыт журнал месяца: ~35 транзакций, итоги доходов/расходов/сальдо
3.  Добавить расход вручную → строка в списке и итоги обновились сразу
4.  Показать панель бюджетов: три категории в разных статусах
    («в норме», «внимание», «превышен») и «доступно в день»
5.  Открыть отчёт месяца: суммы и доли по категориям
6.  Импортировать CSV с битыми строками → отчёт
    «импортировано X, пропущено Y» с номерами строк и причинами
7.  Показать регулярный платёж: шаблон и автоначисление без дублей
8.  Настройки → «Удалить все данные» → база пересоздана пустой
```

Сценарий не зависит от того, что установлено на учебном ПК: сеть
не нужна, права администратора не нужны, демо-база создаётся сама.

Страховка на случай «демо умерло»: приложение запускается и без
базы (первый запуск создаёт пустую), а `--demo` гарантирует
наполненные экраны на любой машине.

## Запуск и сборка

Требования для разработки: .NET 10 SDK.

```powershell
# запуск из исходников
dotnet run --project src/Kopilka.App

# демо-режим
dotnet run --project src/Kopilka.App -- --demo

# юнит-тесты
dotnet test

# демо-сборка для защиты: папка, копирование без установки
dotnet publish src/Kopilka.App -c Release -r win-x64 --self-contained true -o publish
```

После первого запуска данные здесь:

```text
%LOCALAPPDATA%\Kopilka\kopilka.db        (+ kopilka.db-wal, kopilka.db-shm)
%LOCALAPPDATA%\Kopilka\kopilka.demo.db   (режим --demo)
```

## 1. Введение

Наименование программы: **«Копилка»** (Kopilka).

Программа предназначена для ведения личного учёта доходов и расходов на
персональном компьютере под управлением Windows. Пользователь фиксирует
доходы и расходы по счетам и категориям, задаёт месячные бюджеты по
категориям расходов, получает отчёты о структуре трат за месяц, выполняет
импорт и экспорт данных в формате CSV и настраивает регулярные платежи
(например, подписки), которые начисляются автоматически по заданному
расписанию.

Область применения — личные финансы одного пользователя (или семьи на
общем компьютере). Приложение работает полностью локально, сетевое
взаимодействие не предусмотрено.

## 2. Основания для разработки

Основанием для разработки является задание на курсовой проект по дисциплине
«Разработка программных модулей». Требование задания — настольное приложение
на языке C# с интерфейсом на WPF, построенное по архитектурному паттерну
MVVM (Model—View—ViewModel), с подключением локальной базы данных.

Дополнительные требования задания: репозиторий на GitHub с историей работы
по шагам, сопроводительная документация (техническое задание, пояснительная
записка, материалы к защите), покрытие логики юнит-тестами.

## 3. Назначение разработки

### 3.1 Функциональное назначение

Программа предназначена для:

- учёта доходов и расходов по счетам (наличные, карта) и категориям;
- контроля исполнения месячных бюджетов по категориям расходов;
- формирования отчёта о структуре доходов и расходов за месяц;
- обмена данными с электронными таблицами через CSV;
- автоматического создания регулярных платежей по расписанию;
- управления справочниками счетов и категорий.

### 3.2 Эксплуатационное назначение

Пользователь программы — один человек, ведущий личный бюджет. Специальной
подготовки не требуется: интерфейс на русском языке, все операции выполняются
через формы и диалоги. Хранение данных — локальное, на компьютере
пользователя; конфиденциальные данные никуда не передаются.

### 3.3 Границы программы (что не входит в задачу)

Чтобы требования были проверяемыми, зафиксированы и ограничения MVP:

- сетевое взаимодействие отсутствует полностью — ни синхронизации, ни облака;
- мультивалютность не поддерживается: все суммы в рублях;
- многопользовательский режим не поддерживается, пароль на вход не предусмотрен;
- мобильная версия не разрабатывается.

## 4. Требования к программе

### 4.1 Требования к функциональным характеристикам

Функциональные требования перечислены в порядке реализации и разбиты
по группам. Каждая группа закрывает один этап разработки (раздел 6).

**ФТ-1. Счета и категории.**

- ФТ-1.1. Справочник счетов: предустановлены счета «Наличные» и «Карта»;
  пользователь может добавлять собственные счета.
- ФТ-1.2. Справочник категорий: у категории задаются имя и тип — «доход»
  или «расход». Категория расхода может помечаться как категория с лимитом
  (по ней задаётся месячный бюджет).
- ФТ-1.3. Удаление счёта или категории, по которым есть транзакции,
  запрещено — программа сообщает причину отказа.

**ФТ-2. Журнал транзакций.**

- ФТ-2.1. Транзакция содержит: счёт, категорию, сумму, дату и необязательный
  комментарий. Сумма дохода вводится положительной, сумма расхода —
  положительной величиной по категории типа «расход»; знак определяется
  типом категории.
- ФТ-2.2. Журнал показывает транзакции выбранного месяца: дата, счёт,
  категория, комментарий, сумма. Под журналом — итоги месяца: сумма доходов,
  сумма расходов, сальдо.
- ФТ-2.3. Добавление, редактирование и удаление транзакций через диалог.
  Новая транзакция появляется в списке сразу, без перезапуска программы.
- ФТ-2.4. Ввод проверяется: отрицательная или нулевая сумма, категория
  не соответствующего типа — отказ с сообщением причины.

**ФТ-3. Фильтрация и поиск.**

- ФТ-3.1. Журнал фильтруется по категории и по произвольному периоду дат
  (не только календарный месяц).
- ФТ-3.2. Итоговые суммы пересчитываются с учётом фильтра.

**ФТ-4. Бюджеты и контроль лимитов.**

- ФТ-4.1. По категории расхода с признаком лимита задаётся месячный бюджет:
  категория, месяц, сумма лимита.
- ФТ-4.2. Панель бюджетов показывает по каждой категории: лимит, потрачено,
  остаток и статус:
  - «в норме» — потрачено меньше 80 % лимита;
  - «внимание» — потрачено от 80 % лимита включительно и меньше лимита;
  - «превышен» — потрачено не меньше лимита.
- ФТ-4.3. Для статусов «в норме» и «внимание» дополнительно вычисляется
  «доступно в день»: остаток лимита, делённый на число оставшихся дней
  месяца (включая текущий день).

**ФТ-5. Отчёты и CSV.**

- ФТ-5.1. Отчёт за месяц: по каждой категории — сумма и доля в общем объёме
  доходов или расходов; выводится общий итог.
- ФТ-5.2. Экспорт транзакций выбранного месяца в CSV-файл: колонки
  `дата;счёт;категория;сумма;комментарий`, сумма в рублях с копейками.
- ФТ-5.3. Импорт из CSV-файла того же формата. Файл проверяется построчно:
  корректные строки добавляются, некорректные пропускаются. По завершении
  выводится отчёт «импортировано X, пропущено Y» с перечнем пропущенных
  строк и причин (битая дата, отрицательная сумма, неизвестная категория).
  Импорт битого файла не прерывает работу программы.

**ФТ-6. Регулярные платежи.**

- ФТ-6.1. Шаблон регулярного платежа: категория, сумма, день месяца
  (1–31), счёт и признак активности.
- ФТ-6.2. При запуске программы и при открытии месяца создаются транзакции
  по активным шаблонам за пропущенные даты. Если день месяца больше числа
  дней в месяце (например, 31-е в 30-дневном), начисление относится
  к последнему дню месяца.
- ФТ-6.3. Повторное начисление по одной и той же дате исключено:
  уже созданное начисление не дублируется.

**ФТ-7. Настройки и очистка данных.**

- ФТ-7.1. Окно настроек: выбор активного счёта по умолчанию для новых
  транзакций и другие параметры вида «ключ—значение».
- ФТ-7.2. Полное удаление данных: по подтверждению пользователя файл базы
  данных стирается и создаётся заново с чистой схемой и предустановленными
  справочниками.

**ФТ-8. Демонстрационный режим.**

- ФТ-8.1. Запуск с ключом `--demo` использует отдельный файл базы
  `kopilka.demo.db` и заполняет его реалистичными данными одного месяца:
  счета, категории, около 30–40 транзакций, бюджеты и регулярные платежи.
  Демонстрация работает на чистой машине без ручной настройки.

### 4.2 Требования к надёжности

- Вся вводимая информация проходит валидацию до записи в базу; при ошибке
  пользователь получает сообщение с конкретной причиной.
- Ошибочные внешние данные (CSV-файл с битыми строками) не приводят
  к аварийному завершению: обрабатываются построчно, результат — отчёт
  об импорте.
- Миграции схемы базы данных выполняются в транзакции; при сбое миграции
  изменения откатываются, программа сообщает об ошибке и не работает
  с частично обновлённой схемой.
- Версионирование схемы базы данных — через стандартный механизм SQLite
  `PRAGMA user_version`: номер версии хранится в самом файле базы.
- Логика расчётов (статусы бюджетов, генерация регулярных начислений,
  валидация CSV, сальдо) вынесена в отдельные классы без зависимости
  от интерфейса и покрыта юнит-тестами: каждая ветка решения имеет
  хотя бы один тест.
- Проект собирается без ошибок и без предупреждений компилятора; это
  условие проверяется на каждом этапе.

### 4.3 Условия эксплуатации

- Режим эксплуатации — по требованию пользователя, постоянного фонового
  режима нет.
- Данные хранятся локально в каталоге `%LOCALAPPDATA%\Kopilka`; программа
  не требует прав администратора.
- Климатические и механические воздействия не учитываются (обычные условия
  эксплуатации персонального компьютера).
- Восстановление после сбоя питания: база SQLite в журналируемом режиме
  (WAL) сохраняет целостность; максимум потерянного — транзакция, которая
  не была подтверждена.

### 4.4 Требования к составу технических средств

- Персональный компьютер с операционной системой Windows 10/11 (x64).
- Дисковое пространство — порядка 100 МБ с учётом среды выполнения .NET.
- Дополнительных аппаратных требований нет.

### 4.5 Требования к информационной и программной совместимости

- Язык разработки — C#, платформа — .NET (SDK 10).
- Интерфейс — WPF (проект типа `net10.0-windows`).
- Логика и данные — проект библиотеки классов `net10.0` без зависимости
  от WPF: решение состоит из двух проектов, `Kopilka.Core` и `Kopilka.App`.
- База данных — SQLite, доступ через библиотеку `Microsoft.Data.Sqlite`;
  ORM (Entity Framework) не используется, SQL-запросы пишутся напрямую.
- Сторонние библиотеки ограничены перечисленным: `Microsoft.Data.Sqlite`,
  `Microsoft.Extensions.DependencyInjection`,
  `Microsoft.Extensions.Logging`; для тестов — xunit. Прочие пакеты
  не подключаются.
- Файл базы данных хранится по пути `%LOCALAPPDATA%\Kopilka\kopilka.db`
  и совместим между запусками; обмен с внешними системами — только через
  CSV (кодировка UTF-8, разделитель точка с запятой).
- Внутреннее представление сумм — целые копейки (тип `long`), что исключает
  ошибки округления при суммировании; копейки переводятся в рубли только
  на выводе и при экспорте.
- Интерфейс пользователя — русский язык; кодировка исходных файлов — UTF-8.

## 6. Стадии и этапы разработки

Разработка ведётся поэтапно, каждый этап заканчивается сборкой без ошибок
и предупреждений, зелёными тестами, коммитом и записью в журнал. Номер
шага — номер ветки истории в репозитории.

| Шаг | Содержание этапа | Результат (критерий готовности) |
| --- | --- | --- |
| 0 | Каркас решения: два проекта, DI, источники времени `IClock`, пути к данным, пустое главное окно | `Kopilka.Core` собирается без `-windows`; сборка 0 ошибок / 0 предупреждений |
| 1 | Домен, SQLite, миграции схемы, репозитории | База создаётся первым запуском; тесты репозитория зелёные |
| 2 | Каркас MVVM, окно журнала транзакций за месяц с итогами, диалог добавления | Добавленная транзакция видна в списке без перезапуска |
| 3 | Категории, фильтры по категории и периоду, редактирование транзакций | Фильтр работает, итоги пересчитываются |
| 4 | Бюджеты, расчёт статусов, панель бюджетов | Все ветки статуса покрыты тестами |
| 5 | Отчёт месяца по категориям, экспорт и импорт CSV | Импорт битого файла не прерывает работу, даёт отчёт по строкам |
| 6 | Регулярные платежи, генератор начислений | Начисления по шаблонам детерминированы, граничные случаи покрыты тестами |
| 7 | Настройки, полное удаление данных | Удаление стирает базу и пересоздаёт пустую |
| 8 | Режим `--demo`: отдельная демо-база с реалистичным месяцем | Демонстрация работает на чистой машине без ручной настройки |
| 9 | Финальная полировка, README, отчёт, материалы к защите | Полный прогон на чистой папке |

## 7. Порядок контроля и приёмки

Контроль на каждом этапе:

1. `dotnet build` — без ошибок и без предупреждений;
2. `dotnet test` — все тесты успешны; число тестов фиксируется в журнале
   этапа;
3. ручная проверка критерия готовности этапа (таблица раздела 6).

Приёмка в целом:

1. сборка и тесты — как выше, на чистой копии репозитория;
2. демонстрационный сценарий: запуск с ключом `--demo`, затем — добавление
   расхода и пересчёт итогов, установка бюджета и получение каждого
   из трёх статусов, импорт CSV-файла с ошибочными строками (отчёт
   «импортировано X, пропущено Y»), регулярный платёж с начислением,
   полное удаление данных;
3. репозиторий содержит историю коммитов по этапам и документацию
   из раздела 5;
4. пояснительная записка соответствует заданной структуре, названия
   классов и файлов в ней совпадают с фактическими в репозитории.

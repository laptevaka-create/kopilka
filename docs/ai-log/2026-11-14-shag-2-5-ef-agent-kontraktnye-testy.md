# Шаг 2.5 (EF Core) — делегированная часть: контрактные тесты хранилища

Дата: 2026-11-14. Исполнитель: агент. Проверка и приёмка: владелец проекта.

## Задача, поставленная агенту

После основной части перевода данных на EF Core (контекст, конфигурации,
миграция `InitialCreate`, репозитории `Ef*`, DI, 144 теста) делегировано:
закрепить контракт хранилища тестами, которые не проходят через код
репозиториев, — WAL после последовательности старта приложения, поведение
внешних ключей `Restrict` на уровне самой базы (raw-соединение мимо
репозиториев), сохранность сидовых записей при `ResetToSeed`, маппинг
`DateOnly` на границах календаря, конвертер `CategoryKind` в обе стороны,
явная загрузка навигаций; сверить `docs/specs/data-model.md` и дневник
шага с фактической схемой и кодом. Дефекты `src/` не править, а описать
в отчёте с предложением минимального исправления. Правки существующих
тестов без причины, коммиты и пуши запрещены.

## Что выполнил агент

- 8 новых тестов в одном файле `tests/Kopilka.Core.Tests/
  EfStorageContractTests.cs`; фикстура — общая `DatabaseFixture`,
  каждый тест начинается с `ResetToSeed`, WAL-тест работает на
  собственной временной базе:
  - WAL включается raw-PRAGMA до `Database.Migrate()`, читается как
    `wal`, остаётся `wal` после EF-соединений (режим хранится в файле);
  - raw-DELETE счёта с транзакциями → `SqliteException`: `Restrict`
    держит база, а не только логика `DeleteResult`;
  - то же для категории с транзакциями и категории с бюджетом
    (таблица наполняется с шага 4, тест чистит за собой — `ResetToSeed`
    бюджеты не удаляет);
  - `ResetToSeed` после пользовательских данных оставляет ровно сид
    (2 счёта, 6 категорий, 0 транзакций), дублей нет;
  - запись/чтение 29.02.2028 и 31.12.2025 через EF, в столбце — текст
    ISO, високосный день находится выборкой по периоду;
  - обе ветки конвертера `CategoryKind` (в столбце `income`/`expense`);
  - навигации `Transaction.Account`/`Category` без `Include` — null
    (ленивой загрузки нет), с `Include` разрешаются.
- Сборка 0 ошибок / 0 предупреждений, в том числе после удаления
  `bin/`/`obj` во всех четырёх проектах; `dotnet test` — 152 теста
  (77 Core + 75 App), падений нет.
- Вскрытый латентный дефект `src/`: `Delete` в `EfCategoryRepository`
  и `EfAccountRepository` проверяет только `Transactions`, но на
  справочники ссылаются ещё `budgets` (шаг 4) и `recurring` (шаг 6).
  Сценарий: категория без транзакций, но с бюджетом — проверка
  `Any` пропускает, `SaveChanges` падает необработанным
  `DbUpdateException` вместо возврата `DeleteResult.InUse`. Сегодня
  через репозитории не воспроизводится (таблицы пусты), поведение
  унаследовано с шага 1. Предложено: дополнить проверку `InUse` или
  ловить `DbUpdateException`.
- Сверка документации: имена классов/таблиц, `snake_case`-столбцы,
  CHECK на суммах и типе, `Restrict`, `HasData`, `__EFMigrationsHistory`,
  WAL до миграций, версии пакетов, удалённые файлы ручного SQL и числа
  тестов — совпадают. Найдено 7 расхождений формы DDL: нет `DEFAULT`
  (EF пишет значения явно), нет `CHECK` на булевых колонках
  (`has_limit`, `is_active` — гарантия типом `bool`), `UNIQUE`
  реализован именованными индексами, в `recurring` добавлены два
  индекса по внешним ключам, поэтому формулировка дневника «схема не
  изменилась ни на байт» неточна.

# Шаг 2.5 — перевод слоя данных на EF Core

## Задача шага

По замечанию руководителя к ТЗ: доступ к базе данных должен выполняться
через Entity Framework Core. Перевести слой данных с ручного
`Microsoft.Data.Sqlite` на EF Core (контекст, сущности, миграции),
сохранив работоспособность журнала и диалога из шага 2.

## Что сделано

- Пакеты: `Microsoft.EntityFrameworkCore.Sqlite` 10.0.14 +
  `Microsoft.EntityFrameworkCore.Design` (только для генерации миграций,
  `PrivateAssets="all"`); `Microsoft.Data.Sqlite` приходит транзитивно.
  Пакеты `Microsoft.Extensions.*` подняты до 10.0.14 — EF требует
  единые версии, иначе NU1605.
- Сущности: записи-`record` заменены обычными классами EF
  (свойства с `get; set;`); добавлены навигации `Transaction.Account`,
  `Transaction.Category` и аналогичные в бюджетах и шаблонах.
- `KopilkaDbContext`: шесть `DbSet`, конфигурации сущностей в
  `Data/Configurations/*.cs`. Схема сохранена по смыслу: те же таблицы
  и snake_case-столбцы, ключевые CHECK-ограничения (`amount_kopecks > 0`,
  `kind IN ('income','expense')`, день месяца 1–31), уникальность имён
  и пары (категория, месяц), внешние ключи `Restrict` — история
  транзакций неприкосновенна и на уровне базы. Тип категории хранится
  текстом через конвертер значений.
- Миграция `InitialCreate` сгенерирована `dotnet ef`; предустановленные
  счета и категории — `HasData`, попадают в миграцию. Применение —
  `Database.Migrate()` при старте, журнал — `__EFMigrationsHistory`.
- Репозитории `EfAccountRepository`, `EfCategoryRepository`,
  `EfTransactionRepository`: LINQ через `IDbContextFactory`, контекст
  создаётся на операцию в `using`. Интерфейсы репозиториев не менялись —
  фейки в тестах моделей представления не пострадали.
- Приложение: регистрация фабрики контекста в DI, миграции и WAL
  (raw-`PRAGMA`, режим хранится в файле базы) — до показа окна.
- Удалены `SqliteDatabase`, `DatabaseMigrator`, SQL-файл `V001__init.sql`
  и репозитории с ручным SQL.

## Как проверено

- `dotnet build` — 0 ошибок, 0 предупреждений.
- `dotnet test` — 155 тестов зелёных: 80 Core + 75 App (VM-тесты не
  менялись). Core: схема/миграции EF (применённость, идемпотентность,
  все таблицы, журнал миграций, сид), репозитории на реальной
  SQLite-базе (`DbUpdateException` вместо прежнего `SqliteException`),
  контракт хранилища — WAL после последовательности старта приложения,
  `Restrict` на уровне базы (raw-DELETE мимо репозиториев),
  `ResetToSeed` без дублей, `DateOnly` через 29 февраля, обе ветки
  конвертера типа категории, явный `Include` навигаций, `Delete`
  справочника, на который ссылаются бюджет или шаблон.
- Живой прогон: обычный запуск и `--demo` — обе базы создаются
  миграцией EF с нуля, WAL включается, приложение живёт.

## Решения и компромиссы

- **Схема сохранена по смыслу, форма DDL другая.** Таблицы, столбцы и
  ключевые ограничения те же, но EF не ставит `DEFAULT` (значения всегда
  пишутся явно) и не вешает `CHECK` на булевы колонки — 0/1 гарантирует
  тип `bool` в модели; `UNIQUE` реализован именованными индексами
  (`ix_accounts_name`, `ix_budgets_category_month`), а в `recurring`
  добавились два индекса по внешним ключам
  (`IX_recurring_account_id`, `IX_recurring_category_id`). Спека и
  листинг схемы приведены к фактической DDL миграции; старые тесты
  схемы (CHECK, UNIQUE, FK) переехали на EF почти без правок.
- **Ссылки справочников проверяются целиком.** `Delete` категории
  смотрит транзакции, бюджеты и шаблоны, `Delete` счёта — транзакции и
  шаблоны: иначе на шагах 4 и 6 проверка `Any` пропустила бы ссылку,
  `SaveChanges` упал бы необработанным `DbUpdateException` вместо
  `DeleteResult.InUse`. Закрыто сразу, с тестами на обе новые ветки.
- **Классы вместо record.** EF корректно работает и с record, но для
  курсовой канонические сущности с `get; set;` читаются проще и не
  требуют объяснений про init-сеттеры и constructor binding.
- **WAL — raw-PRAGMA до миграций.** EF не даёт штатной настройки
  journal_mode; режим хранится в файле базы, поэтому достаточно
  включить его один раз при старте.
- **Старые dev-базы несовместимы.** Миграции EF стартуют с чистого
  файла; база, созданная версией до EF, вызовет сообщение об ошибке
  подготовки базы. Для разработки это честный сброс:
  `Remove-Item "$env:LOCALAPPDATA\Kopilka\*.db*"` — у пользователей
  релизов ещё нет, миграция схемы на проде не требуется.
- **Контекст на операцию, а не одиночка.** Долгоживущий DbContext
  накапливает отслеживание изменений и не дружит с потоками UI;
  короткие `using` через фабрику — рекомендованный паттерн EF для
  десктопа.
- **Пакетная дисциплина обновлена.** Архитектурный тест теперь
  проверяет белый список с EF-пакетами по всем четырём csproj.

# Шаг 1 — домен, SQLite, миграции, репозитории

## Задача шага

Создать хранилище: доменные записи, база SQLite, миграции схемы
через `PRAGMA user_version` и репозитории за интерфейсами. Критерий
готовности: база создаётся первым запуском, тесты репозитория зелёные.

## Что сделано

- Домен (`Kopilka.Core.Domain`): `Account`, `Category` (с `CategoryKind`),
  `Transaction`, `Budget`, `RecurringPayment`, `Setting` — неизменяемые
  записи; `DeleteResult` — результат удаления справочника
  (`Deleted / NotFound / InUse`).
- Хранилище (`Kopilka.Core.Data`):
  - `SqliteDatabase` — открывает соединение, включает WAL и внешние
    ключи. Соединение одно, на всё время работы приложения;
  - `DatabaseMigrator` — читает версию из `PRAGMA user_version`,
    применяет встроенные в сборку миграции `V###__имя.sql` по порядку,
    каждая в своей транзакции;
  - `V001__init.sql` — шесть таблиц, индексы по датам и категориям,
    предустановленные справочники: счета «Наличные» и «Карта», шесть
    категорий доходов и расходов.
- Репозитории за интерфейсами: `IAccountRepository`,
  `ICategoryRepository`, `ITransactionRepository` и их SQLite-реализации.
  Запросы параметризованы; удаление используемых справочников возвращает
  `InUse` — с причиной, а не молчаливым отказом.
- Контрактные тесты репозиториев: границы периода (первый и последний
  день, соседние месяцы, граница года), ограничение UNIQUE имён,
  спецсимволы в комментариях, смена комментария null ↔ текст,
  несуществующие идентификаторы, порядок при нескольких транзакциях
  в один день.
- Приложение: база открывается и мигрируется до показа окна; в статусной
  строке окна — путь к базе и признак демо-режима. При недоступной базе —
  сообщение и выход без трассировки стека.
- Спецификация `docs/specs/data-model.md`: таблицы, типы, нормализация,
  версионирование, отображение в код.

## Как проверено

- `dotnet build` — 0 ошибок, 0 предупреждений.
- `dotnet test` — 68 тестов, все зелёные: мигратор (версия, идемпотентность,
  все таблицы, сид, WAL, внешние ключи), репозитории счетов, категорий
  и транзакций (CRUD, границы периода включительно, фильтр по категории,
  запрет удаления используемых, CHECK на положительные суммы) и
  контрактные тесты (границы периодов и года, UNIQUE, спецсимволы,
  null ↔ текст, несуществующие id, порядок выборки).
- Живой прогон: обычный запуск создал `kopilka.db` в
  `%LOCALAPPDATA%\Kopilka`, запуск с `--demo` — отдельную
  `kopilka.demo.db`, основная база не затронута.

## Решения и компромиссы

- **Убрала `is_default` из счетов.** Счёт по умолчанию — настройка
  (`settings`), а не флаг справочника: один факт в одном месте,
  иначе два поля разъедутся. Схему в README поправила сразу.
- **Сид категорий в миграции.** ФТ-7.2 говорит о «предустановленных
  справочниках» — заношу две доходные и четыре расходные категории
  сразу: первый запуск открывается не с пустым экраном, а демо-режиму
  на шаге 8 будет из чего выбирать.
- **Миграции встроены в сборку Core.** Репозитории читают их из ресурсов:
  после публикации на чистой машине всё работает без внешних файлов.
- **Тесты изолированы сбросом к сиду.** Первый прогон упал на трёх тестах:
  тесты одного класса мутировали общую базу и зависели от порядка
  выполнения. Добавила `ResetToSeed()` перед каждым тестом — теперь
  каждый начинается с состояния «сразу после миграции».
- **Сумма всегда положительная.** Знак не используется: направление
  задаёт тип категории. CHECK в схеме и тест на вставку нуля/минуса —
  защита на двух уровнях, база не даст записать мусор, даже если
  интерфейс ошибётся.
- **`RETURNING id` вместо `last_insert_rowid()`.** Вставка возвращает
  идентификатор сразу — без отдельного запроса и без гонок.
- **Порядок категорий в ListAll — по типу.** Выборка отдаёт сначала
  расходы, затем доходы, внутри типа по sort_order: списку в интерфейсе
  так группироваться проще. Комментарий интерфейса поначалу описывал
  другой порядок — приведён к фактическому.
